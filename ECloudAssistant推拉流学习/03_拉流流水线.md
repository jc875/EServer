# 03 拉流流水线：从网络收包到屏幕出声出画

> 推流是"打包发快递"，拉流就是"收快递、拆包、还原成原料"。本篇讲 Puller 侧，你会发现它和推流端是镜像关系。

---

## 一、拉流总流水线（和推流对照着记）

```
网络 RTMP/RTSP 流
   │
AVDEMuxer（解封装线程）
   │ av_read_frame 取出 AVPacket
   ├── 视频包 -> H264_Decoder（解码线程）-> YUV420P 转换 -> video_queue
   └── 音频包 -> AAC_Decoder（解码线程）-> 重采样 44.1k S16 -> audio_queue
                                                          │
   videoPlay 线程: 取帧 -> sig_repaint 信号 -> OpenGLRender（GPU贴图）
   audioPlay 线程: 取帧 -> AudioRender::Write -> QAudioOutput 出声
```

**和推流端的镜像关系：**

| 阶段 | 推流端（Pusher） | 拉流端（Puller） |
|---|---|---|
| 数据入口 | WASAPI / GDI 采集 | av_read_frame 读网络 |
| 缓冲 | AudioBuffer | AVQueue（包队列 + 帧队列两级） |
| 编解码 | AAC/H264 编码 | AAC/H264 解码 |
| 格式转换 | S16→FLTP、BGRA→YUV | FLTP→S16、解码格式→YUV420P |
| 输出 | RTMP 分块发走 | OpenGL 贴图 / QAudio 播放 |
| 线程数 | 音频、视频各 1 个 | 读流、解码、播放各线程 |

记忆口诀：**推流是"采集→编码→打包"，拉流是"拆包→解码→渲染"，方向相反，骨架相同。**

## 二、AVDEMuxer：拉流的入口和调度中心

### 1. 构造时就为"低延迟"做的配置（`AVDEMuxer.cpp` 第 5-37 行）

```cpp
av_dict_set(&avDict_, "stimeout", "1000000", 0);       // 套接字超时（微秒）
av_dict_set(&avDict_, "fflags", "nobuffer", 0);        // 尽量不缓存
av_dict_set(&avDict_, "flags", "low_delay", 0);        // 低延迟模式
pFormateCtx_->probesize = 500000;                      // 探测数据量调小，快速起播
pFormateCtx_->interrupt_callback.callback = InterruptFouction; // 中断回调
pFormateCtx_->flags |= AVFMT_FLAG_DISCARD_CORRUPT;     // 丢弃损坏包，不纠缠
```

理由：远程控制场景宁可丢一点数据，也不要卡住等重传。
不足（如实说）：`"tune","zerolatency"` 是编码器选项，放在**解封装输入字典**里其实不生效，属于无效配置；`reconnect` 设成 0 意味着断流不自动重连，网络抖一下就彻底断。

### 2. 中断回调为什么必要

```cpp
int AVDEMuxer::InterruptFouction(void *arg)
{
    AVDEMuxer* thiz = (AVDEMuxer*)arg;
    return thiz->quit_;   // 返回 1（true）就强制让阻塞中的 av_read_frame 立刻退出
}
```

`av_read_frame` 在网络没数据时会**阻塞**。如果用户点了关闭，线程卡在里面 join 不回来，程序就"假死"。中断回调是 FFmpeg 官方提供的逃生门：阻塞期间它会周期性调这个函数，你返回 1，它立刻报错退出。这是网络编程里"可中断阻塞"的标准思路。

### 3. 读流主循环（`FetchStream`，第 81-127 行）

```cpp
while(!quit_ && pFormateCtx_)
{
    AVPacketPtr packet(av_packet_alloc(), ...);   // 每包一个智能指针管理的 packet
    int r = av_read_frame(pFormateCtx_, packet.get());
    if(r == 0) {
        if(packet->stream_index == videoIndex)
            h264Decoder_->put_packet(packet);      // 视频包丢进视频解码器的队列
        else if(packet->stream_index == audioIndex)
            aacDecoder_->put_packet(packet);       // 音频包丢进音频解码器的队列
        else
            av_packet_unref(packet.get());         // 无关包（如脚本）释放
    }
    else {
        av_packet_unref(packet.get());
        break;                                     // 读失败（含中断）退出循环
    }
}
```

注意这里的两级队列设计：**读流线程只负责分发，不亲自解码**。因为解码耗时且可能阻塞，分开后读流线程能持续把网络数据收走，避免 TCP 接收缓冲堆积。

### 4. 流信息探测（`FetchStreamInfo`）

```cpp
avformat_open_input(&pFormateCtx_, path.c_str(), nullptr, &avDict_);
avformat_find_stream_info(pFormateCtx_, nullptr);
for(int i = 0; i < pFormateCtx_->nb_streams; i++) {
    if(... == AVMEDIA_TYPE_VIDEO) videoIndex = i;   // 记下哪条是视频流
    else if(... == AVMEDIA_TYPE_AUDIO) audioIndex = i;
}
h264Decoder_->Open(pFormateCtx_->streams[videoIndex]->codecpar); // 用流参数初始化解码器
aacDecoder_->Open(...);
```

`codecpar`（编解码器参数）就是推流端 `extradata` 里 SPS/PPS、AudioSpecificConfig 经过服务器转发后到达对端的形态——**推流端拼的序列头，在这里被 FFmpeg 自动解析成 codecpar**，这就是为什么发数据前必须先发序列头。

## 三、两个解码器：线程 + 队列 + 格式转换

### 1. H.264 解码线程（`H264_Decoder.cpp`）

```cpp
int H264_Decoder::Open(const AVCodecParameters *codecParamer)
{
    codec_ = avcodec_find_decoder(codecParamer->codec_id);   // 按ID找解码器
    codecCtx_ = avcodec_alloc_context3(codec_);
    avcodec_parameters_to_context(codecCtx_, codecParamer);   // 参数灌进上下文
    codecCtx_->flags |= AV_CODEC_FLAG2_FAST;                  // 快速解码
    avcodec_open2(codecCtx_, codec_, nullptr);

    // 解码输出统一转成 YUV420P，方便 OpenGL 渲染
    videoConver_->Open(width, height, codecCtx_->pix_fmt,
                      width, height, AV_PIX_FMT_YUV420P);
    start();   // QThread 启动 run()
}
```

`run()` 里的标准解码循环（新版 FFmpeg 的 send/receive 模型，你应该熟悉）：

```cpp
while(!quit_) {
    if(!video_queue_.size()) { sleep 1ms; continue; }  // 没包等
    video_queue_.pop(pkt);
    avcodec_send_packet(codecCtx_, pkt.get());         // 送压缩包进去
    while(ret >= 0) {
        ret = avcodec_receive_frame(codecCtx_, yuv_frame_.get()); // 收原始帧
        if(ret == EAGAIN || ret == EOF) break;         // 暂时没帧输出，正常
        videoConver_->Convert(yuv_frame_, outFrame);   // 转 YUV420P
        avContext_->video_queue_.push(outFrame);       // 进帧队列等渲染
    }
}
```

### 2. AAC 解码线程（`AAC_Decoder.cpp`）

结构完全一样，区别在重采样目标：

```cpp
avContext_->audio_sample_rate = 44100;
avContext_->audio_fmt = AV_SAMPLE_FMT_S16;
avContext_->audio_channels_layout = AV_CH_LAYOUT_STEREO;
audioResampler_->Open(codecCtx_->sample_rate, codecCtx_->channels,
                      codecCtx_->sample_fmt,           // 输入：编码器给的格式
                      44100, 2, AV_SAMPLE_FMT_S16);   // 输出：统一 44.1k 双声道整数
```

为什么强制重采样到 44100/S16？因为播放设备 `AudioRender` 初始化时写死了这个格式（`AVPlayer::Init` 第 40 行 `InitAudio(2,44100,16)`）。**先把播放格式定死，再让所有输入都重采样成它**，这是常见的"以输出格式为锚"设计。

### 3. 为什么解码端也用 send/receive 而不是老的 `avcodec_decode_*`

一个 packet 可能解出 0 个、1 个或多个 frame（B 帧重排、缓存延迟），send/receive 把"喂"和"取"解耦，用 `EAGAIN` 表示"现在没货，待会儿再取"，语义清晰。你在 GDI 采集的解码里也能看到同一个模型，**这是全项目反复出现的共同模式，值得记住。**

## 四、AVQueue：线程安全的链表队列

`AV_Queue.h` 是解码器和播放器之间的缓冲：

```cpp
template<typename T>
class AVList {
    void push(const T& value) {
        lock(mutex);
        Node* node = new Node(value);     // 新节点挂到尾部
        if(tail_) { tail_->next = node; node->prev = tail_; tail_ = node; }
        else head_ = tail_ = node;
        ++size_;
    }
    bool pop(T& value) {
        lock(mutex);
        if(!head_) return false;
        ... 从头部摘节点、delete、--size_
    }
};
```

- 双向链表 + 互斥锁，`push` 的线程（解码器）和 `pop` 的线程（播放器）各干各的，靠锁保护。
- 与推流端 `AudioBuffer` 的区别：**这里是无界队列**（没有最大长度限制）。

如实说不足：
1. 无界队列在网络快、播放慢时会无限增长，**内存一路涨**，这是直播客户端最常见的内存问题之一。工业级实现要加最大长度，满了就丢非关键帧或让解码线程等待。
2. 每个节点单独 `new/delete`，高频小包场景分配开销大，更好的做法是对象池/内存池复用节点。
3. 只有互斥锁、没有条件变量（`condition_variable`），消费者只能 sleep 1ms 轮询，存在唤醒延迟和空转。

## 五、两个渲染器：最终把数据变成画面和声音

### 1. OpenGLRender：GPU 贴图（`OpenGLRender.h`）

```cpp
QOpenGLTexture* texY_; QOpenGLTexture* texU_; QOpenGLTexture* texV_;
```

注意它建了 **Y、U、V 三张纹理**，因为输入是 YUV420P 平面格式（Y 一张全分辨率图，U/V 各一张 1/4 分辨率图）。渲染流程：

1. 收到 YUV 帧，分别上传到三张纹理；
2. 着色器（`vertex.vsh`/`fragment.fsh`）里做 YUV→RGB 矩阵转换；
3. GPU 直接输出，不占 CPU。

为什么用 YUV 而不是直接 RGB？这是历史和工程双重原因：摄像头/编码器天然输出 YUV；YUV420P 里色度只占 1/4 体积，带宽省；GPU 转 RGB 几乎零成本。

视频播放线程通过 Qt 信号槽跨线程投递：

```cpp
// videoPlay() 工作线程里
sig_repaint(frame);                          // 发信号
// Init() 里绑定：QueuedConnection 保证槽函数在 UI 线程执行
connect(this, &AVPlayer::sig_repaint,
        this, &OpenGLRender::Repaint, Qt::QueuedConnection);
```

**为什么必须 QueuedConnection？** OpenGL 上下文只能在 UI（GUI）线程调用，工作线程直接碰 GL 会崩溃。队列连接把调用"投递"到 UI 线程的事件循环里执行，这是 Qt 跨线程更新界面的铁律。

### 2. AudioRender：QAudioOutput 出声（`AudioRender.cpp`）

```cpp
bool InitAudio(int nChannels, int SampleRate, int nSampleSize) {
    audioFmt_.setCodec("audio/pcm");
    audioFmt_.setByteOrder(QAudioFormat::LittleEndian);
    audioFmt_.setSampleType(QAudioFormat::SignedInt);  // 对应 S16
    audioFmt_.setChannelCount(nChannels);
    audioFmt_.setSampleRate(SampleRate);
    audioOut_ = new QAudioOutput(audioFmt_);
    audioOut_->setBufferSize(409600);
    device_ = audioOut_->start();           // start 返回一个 QIODevice，往里 write 就出声
}

void Write(AVFramePtr frame) {
    QByteArray audioData((char*)frame->data[0],
        (frame->nb_samples * frame->channels) * (nSampleSize_/8));
    device_->write(audioData.data(), audioData.size());
    av_frame_unref(frame.get());
}
```

播放线程（`AVPlayer::audioPlay`）先看设备还有没有空间再写：

```cpp
if(!AvailableBytes() || audio_queue_.empty()) { sleep 1ms; continue; }
// AvailableBytes = bytesFree - periodSize，留出一个周期余量，防止写满阻塞
```

### 3. 如实说音频渲染的问题

1. `frame->channels` 在新版 FFmpeg 中已废弃，应使用 `frame->ch_layout.nb_channels`。当前能编译（带警告），升级大版本 FFmpeg 可能直接编不过。
2. `Write` 里用 `nb_samples * channels * 2` 手工算字节，假设了 packed S16 双声道。一旦上游格式变化（比如单声道），这里没有任何断言保护，会读出越界垃圾数据。
3. `new QAudioOutput` 没有对应 `delete`，靠进程退出回收，严格来说是泄漏（虽然对象生命周期跟窗口一样长，实际危害小）。

## 六、AVPlayer 的整体串接与一个崩溃隐患

`HandleStartStream`（收到信令服务器的"开始拉流"回调后）：

```cpp
avDEMuxer_->Open(streamAddr.toStdString());           // 启动读流线程
audioThread_.reset(new std::thread([this](){ audioPlay(); }));
videoThread_.reset(new std::thread([this](){ videoPlay(); }));
```

信令通道（`SigConnection`）和媒体通道分离：信令服务器只负责告诉它"拉哪个地址、什么时候停"，真正的音视频从 `streamAddr`（RTMP/RTSP 地址）独立拉取。这和 ENET 里 SigServer 的设计是同一套思路。

**崩溃隐患（`Close`，第 45-65 行）：**

```cpp
void AVPlayer::Close() {
    stop_ = true;
    if(audioThread_->joinable()) { ... }   // 若还没 Start 就 Close，audioThread_ 是空指针！
    if(videoThread_->joinable()) { ... }   // 对空 unique_ptr 调用 -> 直接崩溃
}
```

`unique_ptr` 默认是 nullptr，未启动流就关闭（或重复 Close）时，`nullptr->joinable()` 是未定义行为，Windows 上直接访问违例。正确写法先判 `if(audioThread_ && audioThread_->joinable())`。
