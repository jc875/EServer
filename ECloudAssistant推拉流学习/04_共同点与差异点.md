# 04 共同点与差异点：跨代码的可迁移骨架 + Bug 总清单

> 这份文档回答你那句"这么多代码肯定有能总结出来的点"。结论先行：**音视频项目的类看起来多，其实都在重复同一套骨架，变的只是每段的具体技术选型。**

---

## 一、六段通用骨架（所有音视频代码都能往里套）

```
① 采集 Source   → ② 缓冲 Queue → ③ 编解码 Codec →
④ 封装/解封装 Mux → ⑤ 传输 Transport → ⑥ 渲染 Sink
```

拿到任何一份陌生音视频代码，先给每个类标注它属于哪一段，立刻就不慌了。

| 段 | 职责 | 本项目对应类 | 输入→输出 |
|---|---|---|---|
| ① 采集 | 从系统设备取原始数据 | WASAPICapture、GDIScreenCapture | 系统API → PCM/BGRA |
| ② 缓冲 | 线程间解耦、削峰填谷 | AudioBuffer、AVQueue、AVList | 原始数据暂存 |
| ③ 编解码 | 压缩/还原 | AudioEncoder、VideoEncoder、两个 Decoder | PCM↔AAC、BGRA↔H264 |
| ④ 封装 | 按协议打包/拆包 | RtmpPublisher、AVDEMuxer、RtmpChunk、amf | 裸帧↔协议消息 |
| ⑤ 传输 | 网络收发 | RtmpConnection、TcpConnection、EventLoop | 字节流 |
| ⑥ 渲染 | 还原成感官信号 | OpenGLRender、AudioRender | YUV/PCM → 画面/声音 |

### 每段的共同设计模式（面试可以直接说）

1. **采集段**：回调（callback）或轮询两种数据交付方式；独立线程 + 启停状态机（init/start/stop/exit 四件套）；删除拷贝构造保证设备唯一。
2. **缓冲段**：互斥锁保护读写游标；生产者-消费者模型；用"帧/字节"两种单位换算。
3. **编解码段**：上下文（AVCodecContext）+ send/receive 两函数；`extradata` 存全局参数；格式不符就先挂转换器（swr/swscale）。
4. **封装段**：手工拼协议头（字节序、长度字段）；序列头先发；状态机驱动信令。
5. **传输段**：Reactor/EventLoop 非阻塞模型；消息分块；连接状态可查询。
6. **渲染段**：UI 线程约束（QueuedConnection）；以输出格式为锚，上游全部转换适配。

## 二、不同代码的差异点（同一段里换技术，骨架不变）

### 1. 采集端的平台差异

| 平台 | 音频采集 | 屏幕/视频采集 |
|---|---|---|
| Windows | WASAPI（本项目）、DirectSound、WDM-KS | GDI（本项目）、DXGI Desktop Duplication、DShow |
| Linux | ALSA、PulseAudio、PipeWire | X11 XShm、PipeWire、V4L2（摄像头） |
| macOS | CoreAudio | ScreenCaptureKit、AVFoundation |
| 跨平台库 | FFmpeg 输入设备（dshow/alsa 等）、Qt Multimedia、miniaudio、PortAudio | 同左 |

**关键认知**：WASAPI、ALSA、CoreAudio 名字完全不同，但初始化流程全是"枚举设备 → 选设备 → 配格式 → 起线程 → 循环取包 → 释放缓冲"，连 bug 类型都相似（格式协商失败、缓冲不释放、线程启停顺序）。

### 2. 协议差异

| | RTMP（本项目） | RTSP/RTP | WebRTC |
|---|---|---|---|
| 连接模型 | 长连接 TCP | 信令 TCP + 媒体 UDP/RTP | UDP + P2P/中继 |
| 打包单位 | Chunk + Tag | RTP 包 + 载荷 | RTP/SRTP |
| 握手 | C0/C1/C2 + AMF | DESCRIBE/SETUP/PLAY | ICE/DTLS/SRTP |
| 延迟 | 1-3 秒 | 1 秒左右 | 200-500ms |
| 共同点 | 都要握手、都有序列头协商、都有时间戳、都要分块/分包 | 同左 | 同左 |

### 3. 推流 vs 拉流的差异（方向相反，类名成对）

```
WASAPICapture  ↔ AudioRender        （声卡取 vs 声卡放）
GDIScreenCapture ↔ OpenGLRender     （屏幕取 vs 屏幕画）
AACEncoder     ↔ AAC_Decoder        （FLTP 进 vs S16 出）
RtmpPublisher  ↔ AVDEMuxer          （手工拼 Tag vs 自动拆 Tag）
RtmpConnection ↔ TcpConnection      （切块发 vs 收字节）
```

### 4. 缓冲实现的差异与取舍

| | AudioBuffer | AVQueue/AVList |
|---|---|---|
| 结构 | 连续 vector + 双游标 | 双向链表 |
| 回收 | erase 前移（O(n)） | 节点 delete |
| 容量 | 有界，满了丢数据 | 无界，可能涨内存 |
| 适用 | 实时音频（不能无限缓存） | 解码帧中转 |
| 共同问题 | 都只有锁、没有条件变量，靠 sleep 轮询 | 同左 |

## 三、反复出现的 5 个通用思想（这是最值钱的部分）

1. **生产者-消费者 + 缓冲解耦**：全项目出现 6 次以上（WASAPI→AudioBuffer、GDI→帧、DEMuxer→Decoder→Render）。凡是两个环节速度不匹配，就插队列。
2. **四件套生命周期**：`init → start → stop → exit/close`，每个类都有，且讲究顺序（先 join 线程再关设备、先建采集再建编码）。
3. **send/receive 与 EAGAIN**：编解码、队列读取都用"尝试取，没货返回 EAGAIN/失败，调用方稍后重试"的非阻塞语义。
4. **格式协商链**：数据格式永远在"协商/转换"——float↔int、packed↔planar、BGRA↔YUV、采样率 48k↔44.1k。转换对象（swr/swscale）是独立可替换的类。
5. **智能指针管资源**：`ComPtr`（COM）、`unique_ptr/shared_ptr + default_delete[]`（数组）、带自定义删除器的 AVFrame/AVPacket，本质都是 RAII——**资源申请和释放绑定对象生命周期，防止泄漏**。

## 四、Bug 总清单（全部基于真实代码，按严重程度排序）

### 硬伤级（会导致功能错误或崩溃）

| # | 位置 | 问题 | 正确做法 |
|---|---|---|---|
| 1 | WASAPICapture::adjustFormatTo16Bits | 只改格式标签，数据仍是 float32，Initialize 可能失败或出噪声 | 保留原格式，用 swr/手工 float→s16 转换；或 IsFormatSupported 先问 |
| 2 | WASAPICapture::capture | 静音时清零 m_pcmBuf，回调却传原始 pData | 回调统一传 m_pcmBuf.get() |
| 3 | RtmpPublisher::IsKeyFrame（两处） | 起始码判断条件写反，3 字节 `00 00 01` 匹配不上，关键帧识别失效 | 判断 data[2]==1（3字节）/ data[3]==1（4字节） |
| 4 | RtmpPushManager::PushVideo | 无脑 size-4，遇 3 字节起始码多切一字节 | 按实际 startcode 长度切 |
| 5 | AVPlayer::Close | 未启动流就关闭时，对空线程指针 joinable() 崩溃 | 先判空再 join |
| 6 | GDIScreenCapture::Decode | frame_size_ 用 pkt_size，原始帧该字段无意义，帧长度错误 | 用 width*height*4 或 linesize 累计 |

### 设计级（能跑但有隐患）

| # | 位置 | 问题 |
|---|---|---|
| 7 | RtmpPublisher | AAC 序列头错走 SendVideoData；音频在首个视频关键帧前全丢 |
| 8 | AudioBuffer | 非真环形，erase 整体前移 O(n)；写满静默丢数据无统计 |
| 9 | AVQueue | 无界队列可能内存无限涨；节点频繁 new/delete；无条件变量靠轮询 |
| 10 | 时间戳 | 音视频各自 Elapsed()，无主时钟对齐，长期可能音画不同步 |
| 11 | 分辨率/格式 | 2560x1440、44100 多处写死，换设备即失败 |
| 12 | AVDEMuxer | 输入字典里放 zerolatency 等编码选项，实际不生效；reconnect=0 不自动重连 |
| 13 | AudioRender | 使用已废弃的 frame->channels；手工算长度无格式断言；QAudioOutput 未释放 |
| 14 | 帧率 | GDI 25fps 与编码线程 30fps 不一致，节奏漂移 |
| 15 | COM | CoInitialize 失败（如公寓模式冲突）未检查返回值；析构路径靠 exit 配对 |

### 面试时怎么说这些不足（不美化但显水平）

不要说"这代码垃圾"，要说"**它完成了教学目标，但在 X 场景下有 Y 风险，工业级应该用 Z 方案**"。例如：
> "AudioBuffer 用 vector erase 实现回收，功能正确但 O(n) 搬运，在 48k 双声道每秒上百次回调下有持续 CPU 开销；生产环境我会改成定长环形缓冲加条件变量，满了按高水位丢最旧帧并计数。"

## 五、读新代码的标准动作（已固化进 av-pipeline-analysis skill）

1. 先列目录，给每个类贴六段骨架标签；
2. 找 `main/Init/Open`，按创建顺序画出依赖链；
3. 找线程函数和回调，标出谁生产谁消费、队列在哪；
4. 追格式：每个数据结构进入下一段前发生了什么转换；
5. 对照 bug 清单逐项检查（起始码、格式标签、空指针 join、缓冲容量、时间戳）；
6. 输出时：先讲背景概念 → 生活类比 → 逐行真实代码 → 如实说不足，不猜测、不美化。
