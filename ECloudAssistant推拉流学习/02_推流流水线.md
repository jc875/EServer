> 接上一篇。本篇把 "取到货以后怎么加工、怎么发走" 讲透，全部基于真实代码。

## 一、先看推流端的总流水线（背下来这张图）



```
[系统声卡] --WASAPI--> PCM回调 --+
                                 |
                          AudioBuffer（线程间缓冲）
                                 |
   音频线程 EncodeAudio(): 攒够一帧 -> AAC编码 -> 0xAF音频Tag --+
                                                               |
[屏幕] --gdigrab--> BGRA帧 -- 视频线程 EncodeVideo():          |
                   H264编码 -> 0x17/0x27视频Tag ---------------+
                                                               |
                                              RtmpConnection（分块Chunk）
                                                               |
                                                    TCP socket -> 服务器
```

**核心设计思想：生产者 - 消费者模型 + 线程解耦。**

生活类比：奶茶店 ——



* 采集器是后厨，按自己的节奏做原料（WASAPI 有数据就回调、GDI 每秒 25 帧）；

* 缓冲（AudioBuffer / 队列）是取餐台，后厨和前台速度不一样也不会互相卡住；

* 编码线程是打包员，按 "订单要求的规格"（AAC 一次要 1024 帧、H.264 一帧一帧）取货打包；

* RTMP 是快递，把包裹按统一格式分箱（Chunk）发走。

为什么必须解耦？因为各环节速度不同且会抖动：声卡回调时机不固定、编码耗时波动、网络会堵。**没有缓冲，最慢的环节会卡死所有环节；有了缓冲，各环节各跑各的线程。**

### 特别说明：视频这条线其实没有回调、也没有队列（别被图的对称误导）

上面那张图把音视频画成了对称的两条线，看起来视频也该有 "回调 + 中间队列"。**实际上没有，这是图简化后容易误会的地方，必须单独讲清。** 两条线的交接方式根本不同：



| 对比项    | 音频（WASAPI）                     | 视频（GDI 抓屏）                         |
| ------ | ------------------------------ | ---------------------------------- |
| 交接方式   | **推（push）**：系统有数据就触发回调         | **拉（pull）**：视频线程主动来取               |
| 中间结构   | 有 `AudioBuffer` 排队，能攒多包        | **没有队列**，只在采集器里留 "最新一帧"            |
| 数据会不会丢 | 队列里按顺序排着                       | 只保留最新帧，来不及取就被新帧覆盖                  |
| 真实代码   | `WASAPICapture` 的 `m_callback` | `GDIScreenCapture::CaptureFrame()` |

看真实代码：



* `GDIScreenCapture` 自己是一个 QThread，`run()` 里每秒抓 25 帧，解码后**覆盖式**写进成员 `rgba_frame_`（用 `mutex_` 保护），它只存 "当前最新一帧"，不是排队。

* 视频线程 `EncodeVideo()` 循环里**主动调** `screen_Capture_->CaptureFrame(...)`（`RtmpPushManager.cpp` 第 169 行），把最新帧拷走再编码 —— 这是拉模式。

* 全程没有回调函数，也没有视频队列。

生活类比：音频像**外卖送货上门**（有数据就敲门推给你，门口还能排队放几单）；视频像**公告栏贴通知**，采集器只管把最新一张贴上去，旧的被新的盖住，你想知道就自己走过去看（CaptureFrame），看到的永远是当下那张。

这个设计的代价也要如实说：视频处理慢于采集时，中间帧会被直接覆盖丢弃（丢帧），但屏幕画面丢一两帧不影响理解，反而省内存；而音频不能这么干，丢音频会出现爆音 / 断流，所以音频才专门配了队列。

## 二、AudioBuffer：一个 "伪环形缓冲" 的实现与问题

`AudioCapture` 不直接把数据传给编码器，而是写进 `AudioBuffer`（`AudioBuffer.h`）。先看它的设计：



```
// 两个游标：读位置、写位置
size_t _readerIndex = 0;
size_t _writerIndex = 0;

uint32_t readableBytes() const { return _writerIndex - _readerIndex; }  // 还能读多少
uint32_t writableBytes() const { return _buffer.size() - _writerIndex; }// 还能写多少
```

### 写入（第 23-41 行）



```
int write(const char *data, uint32_t size)
{
    std::lock_guard<std::mutex> lock(_mutex);   // 加锁：采集线程和读取线程都会访问
    uint32_t bytes = writableBytes();
    if (bytes < size) size = bytes;             // 写不下就截断！（问题点1）
    if (size > 0) {
        memcpy(beginWrite(), data, size);
        _writerIndex += size;
    }
    retrieve(0);                                // 尝试搬运、回收头部空间
    return size;
}
```

### 读取（第 43-55 行）



```
int read(char *data, uint32_t size)
{
    std::lock_guard<std::mutex> lock(_mutex);
    if (size > readableBytes()) { retrieve(0); return -1; }  // 数据不够
    memcpy(data, peek(), size);
    retrieve(size);                            // 读多少，游标前进多少
    return size;
}
```

### 它怎么 "回收" 空间（`retrieve`，第 97-119 行）



```
void retrieve(size_t len) {
    if (len > 0) {
        _readerIndex += len;
        if (_readerIndex == _writerIndex)      // 读空了，两个游标归零
            _readerIndex = _writerIndex = 0;
    }
    if (_readerIndex > 0 && _writerIndex > 0) {
        // 把头部已经读过的数据"删掉"，后面的数据整体往前搬
        _buffer.erase(_buffer.begin(), _buffer.begin() + _readerIndex);
        _buffer.resize(_bufferSize);
        _writerIndex -= _readerIndex;
        _readerIndex = 0;
    }
}
```

### 如实说不足（三个问题）



1. **它不是真环形缓冲**。真环形缓冲（ring buffer）写满后绕回头部，内存位置固定，没有数据搬运。这里每次都 `erase + resize`，`vector::erase` 会把后面所有元素整体前移，是 O (n) 操作，数据量大时白白耗 CPU。

* 正确做法：用取模运算 `_writerIndex = (_writerIndex + size) % _bufferSize`，首尾相连。

1. **写满直接丢数据**（`if (bytes < size) size = bytes`），没有任何告警。音频丢包会出现 "咔哒" 声或断音。至少应该统计丢包字节数，方便排查。

2. **单缓冲无水位控制**，消费者无法知道 "快满了 / 快空了"，工业级实现会有高水位（满了让生产者减速）和低水位（不足时消费者等待）。

### 上层怎么用它（`AudioCapture.cpp`）



```
// 采集线程：WASAPI 每来一包，回调里写进缓冲
capture_->setCallback([this](const WAVEFORMATEX *mixFormat,
                             uint8_t *data, uint32_t samples){
    audio_buffer_->write((char*)data, mixFormat->nBlockAlign * samples);
});

// 消费侧：先问有多少帧，够了才读
int AudioCapture::GetSamples() {
    return audio_buffer_->size() * 8 / bits_per_sample_ / channels_;
}
int AudioCapture::Read(uint8_t *data, uint32_t samples) {
    if(samples > this->GetSamples()) return 0;   // 不够就不读
    audio_buffer_->read((char*)data,
        samples * bits_per_sample_/8 * channels_);
    return samples;
}
```

注意这里的单位换算：缓冲里存的是**字节**，对外说的是**采样帧数**，靠 `字节*8/位深/声道` 换算。

## 三、总指挥：RtmpPushManager 的初始化顺序

`RtmpPushManager::Init()`（第 48-119 行）是理解整个推流端的钥匙。它的创建顺序是有讲究的：



```
bool RtmpPushManager::Init()
{
    pusher_ = RtmpPublisher::Create(loop_);     // ① 推流器（先有发货渠道）
    pusher_->SetChunkSize(60000);               //    RTMP 分块大小

    screen_Capture_.reset(new GDIScreenCapture()); // ② 屏幕采集
    if(!screen_Capture_->Init()) return false;

    h264_encoder_.reset(new H264Encoder());    // ③ H.264 编码器
    if(!h264_encoder_->OPen(2560,1440,30,80000,AV_PIX_FMT_BGRA))
        return false;                          // 2560x1440、30帧、80kbps 目标

    audio_Capture_.reset(new AudioCapture());  // ④ 音频采集（内部起 WASAPI）
    if(!audio_Capture_->Init()) return false;

    aac_encoder_.reset(new AACEncoder());     // ⑤ AAC 编码器
    if(!aac_encoder_->Open(audio_Capture_->GetSamplerate(),
                           audio_Capture_->GetChannels(),
                           AV_SAMPLE_FMT_S16, 64))
        return false;
    ...
    pusher_->SetMediaInfo(mediaInfo);          // ⑥ 把编解码参数交给推流器
}
```

### 为什么顺序不能乱？



* 编码器初始化参数（采样率、声道数）要**从采集器实际格式里读**（第 77 行），所以采集器必须先建。

* 推流器要先发 "序列头"（SPS/PPS、AudioSpecificConfig），这些参数从编码器的 `extradata` 里拿，所以编码器要先建好。

* 生活类比：先确认原料规格（采集格式），再调机器（编码器），最后告诉快递员包裹长什么样（媒体信息）。

### 什么是 extradata / 序列头？为什么必须先发？

#### 1. 先搞懂 extradata 是什么

编码器的 `AVCodecContext` 里有一块单独的内存叫 `extradata`，专门放 "**这一路流的全局参数**"。本工程开了 `AV_CODEC_FLAG_GLOBAL_HEADER`，意思是让编码器把 SPS/PPS 这种全局信息**不塞进每一帧，而是集中放到 extradata**，由我们取出来单独发。



* **H.264 产出 SPS 和 PPS**：


  * **SPS（Sequence Parameter Set，NAL 类型 7）**：序列参数，告诉解码器画面多大、什么 profile/level、帧率等 "全局规格"。

  * **PPS（Picture Parameter Set，NAL 类型 8）**：图像参数，告诉解码器每帧怎么解（熵编码方式等）。

* **AAC 产出 AudioSpecificConfig**：通常 2 字节，里面编码了采样率索引、声道索引等，解码器据此知道该按什么规格解 AAC。

#### 2. 为什么必须 "先发"，而且要在媒体数据之前

解码器刚启动时是一张白纸，不知道画面尺寸、档次、采样率。这时候你直接塞一个 P 帧给它，它**没有上下文，解不出来**。所以任何媒体帧之前，必须先把 "配置说明书" 发过去：



* RTMP 是**流式**协议，没有额外通道，配置只能作为一种特殊消息在流最前面发，这就是 "**序列头**"。

* 对端（或服务器、播放器）收到序列头后先初始化解码器，之后收到的媒体帧才解得出。

* 序列头一般在连接建立、推流开始时发一次；中途参数不变就不用重发。

生活类比：序列头像**入职第一天发的员工手册**（公司架构、规章制度），先读完手册，后面每天的具体工作（媒体帧）你才知道怎么干；没发手册直接派活，新人完全懵。

#### 3. 真实代码：从 extradata 到序列头，分三步

**第一步：从编码器取出 extradata**（`RtmpPushManager.cpp` 第 88-93 行）



```
int extradatdSize = h264_encoder_->GetSequenceParams(extradata,1024);
// 内部就是把 AVCodecContext::extradata 拷到本地缓冲
```

**第二步：用 H264Paraser 在里面定位 SPS、PPS**（第 95-109 行）



```
H264Paraser::Nal sps = H264Paraser::findNal(extradata, extradatdSize);
if (... && (*sps.first & 0x1f) == 7) {        // NAL 头字节低5位=7 → SPS
    ... 拷贝 SPS
    H264Paraser::Nal pps = H264Paraser::findNal(sps.second, ...);
    if (... && (*pps.first & 0x1f) == 8)      // 低5位=8 → PPS
        ... 拷贝 PPS
}
```



* `findNal` 返回一对指针（NAL 头、NAL 尾），靠识别起始码 `00 00 01` / `00 00 00 01` 来切分。

* NAL 类型判断：NAL 头字节**低 5 位**（`& 0x1f`）就是类型号，7=SPS、8=PPS、5=IDR。

* AAC 同理，`GetSpecificConfig` 取出 AudioSpecificConfig（第 111-116 行），全部装进 `MediaInfo`。

**第三步：SetMediaInfo 把它们包装成 RTMP 序列头**（`RtmpPublisher.cpp` 第 21-99 行）

视频侧手工拼一个叫 **AVCDecoderConfigurationRecord** 的结构：



```
0x17            关键帧+AVC 的视频 Tag 头
0               第二字节=0 表示"序列头"（媒体数据这里是 1）
00 00 01        固定版本
sps[1..3]       profile / 兼容 / level
0xFF 0xE1       保留 + SPS 个数=1
SPS长度(2字节) + SPS 本体
0x01 + PPS长度(2字节) + PPS 本体
```

音频侧：



```
0xAF            AAC 音频 Tag 头
0               0=AAC 序列头（1=原始 AAC 数据）
AudioSpecificConfig（2字节）
```

**记住这个区分**：第二字节 **0 = 序列头，1 = 真正的媒体数据**；Tag 头 `0x17` 是视频、`0xAF` 是 AAC。

#### 4. 如实说这里的问题



* `H264Paraser::findNal` 结尾有个 bug：`nal.second == nullptr;` 用了 `==` 比较而不是赋值，等于什么也没做（第 76 行）。

* 它的起始码识别对 3 字节起始码的处理也有已知问题（前面 bug 清单里讲过），在本工程这种特定数据下可能影响 NAL 边界，需要警惕。

* 序列头缓冲直接 `new char[4096]` 固定大小，SPS/PPS 异常大时有越界风险（当前参数下不会触发）。

## 四、视频线程：GDI 采集 → H.264 编码 → 推送

`EncodeVideo()`（第 138-181 行）：



```
void RtmpPushManager::EncodeVideo()
{
    static Timestamp timeStamp;
    uint32_t fameRate = 30;
    while(!exit_ && isConnect)
    {
        // —— 帧率控制：目标每 30ms 一帧 ——
        uint32_t elapsed = timeStamp.Elapsed();
        uint32_t delay = fameRate;
        if(elapsed > delay) delay = 0;          // 已经超时就别睡了，立刻赶工
        else delay -= elapsed;
        std::this_thread::sleep_for(std::chrono::milliseconds(delay));
        timeStamp.Reset();

        FrameContainer bgra_image;
        // ① 从 GDI 采集器取一帧 BGRA（它内部线程已把最新帧备好）
        if(screen_Capture_->CaptureFrame(bgra_image, width, height))
        {
            FrameContainer out_frame;
            // ② 编码成 H.264
            if(h264_encoder_->Encode(&bgra_image[0], width, height,
                                     bgra_image.size(), out_frame) > 0)
            {
                if(out_frame.size() > 0)
                    PushVideo(&out_frame[0], out_frame.size());  // ③ 推
            }
        }
    }
}
```

### GDI 采集器内部长什么样（`GDISreenScapture.cpp`）

它其实是**套了 FFmpeg 的一层**，用的是 `gdigrab` 设备：



```
avdevice_register_all();                                  // 注册设备库
input_format_ = const_cast<AVInputFormat*>(
    av_find_input_format("gdigrab"));                    // 找到 GDI 抓屏格式
av_dict_set(&options, "video_size", "2560x1440", 1);      // 屏幕尺寸
av_dict_set_int(&options, "draw_mouse", 1, ...);         // 连鼠标一起录
avformat_open_input(&format_context_, "desktop",
                    input_format_, &options);             // 打开"desktop"输入
```

它自己继承 `QThread`，`run()` 里按 25fps 循环 `av_read_frame` → 解码 → 把最新一帧存起来，等 `CaptureFrame()` 来取。这又是一个 "后台线程生产 + 主线程按需取最新帧" 的模式。

#### 采集线程的循环到底怎么向系统 "要" 数据（重点展开）

这里要讲清你关心的点：**GDI 工具类内部确实有一个线程，在循环里主动去抓数据。** 调用链是三层，全部在 `GDISreenScapture.cpp`：



```
QThread::start() 启动后，操作系统在新线程执行 run()
        │
   run()：while(!stop_) 循环
        ├─ sleep(1000/25)        按 25fps 控制节奏，每秒抓 25 次
        └─ GetOneFrame()         每轮要一帧
              ├─ av_read_frame()  向 FFmpeg 要一个 packet
              │                  （gdigrab 内部再向 Windows GDI 抓桌面位图）
              └─ Decode()         是视频流就解码
                    ├─ avcodec_send_packet()    送压缩包
                    ├─ avcodec_receive_frame()  收原始 BGRA 帧
                    └─ 加锁 → 覆盖写 rgba_frame_（最新帧）
```

逐段理解：



1. `run()`**&#x20;是发动机**：`while(!stop_)` 一直转，每轮先睡 `1000/25 = 40ms` 保证 25fps，再调 `GetOneFrame()`。这是 "定时主动去要"，不是系统推给它。

2. `GetOneFrame()`**&#x20;负责取货**：`av_read_frame()` 从 gdigrab 读一个压缩 packet；判断是视频流就交给 `Decode()`，最后 `av_packet_unref` 释放复用。

3. `Decode()`**&#x20;负责解码并更新最新帧**：用 send/receive 模型，拿到原始 BGRA 帧后**加锁**，把 `rgba_frame_` 整块替换成新帧（旧的被覆盖，所以是 "只留最新一帧"）。

4. 视频线程那边的 `EncodeVideo()` 再通过 `CaptureFrame()` 把这一帧拷走编码。

**和音频的关键区别再强调一次**：音频 WASAPI 是系统有数据就**回调推给你**（被动接收）；视频 GDI 是这个后台线程**定时主动去&#x20;**`av_read_frame`**&#x20;要**（主动拉取）。一个是 "敲门送货"，一个是 "定闹钟去取"。

### 如实说 GDI 这边的两个问题



1. `frame_size_ = av_frame->pkt_size`**&#x20;不可靠（第 260 行）**。解码后的 `AVFrame` 是原始帧，`pkt_size` 是压缩包时代的字段，对原始帧没有正确意义。BGRA 帧大小应该是 `width * height * 4`（或按 `linesize` 累计）。用错字段会导致 `CaptureFrame` 拷贝的长度不对。

2. **分辨率两处写死**（GDI 的 `2560x1440` 和编码器的 `2560,1440`），换一台 1080p 电脑直接失败。代码注释自己也承认了。工业级做法是先 `GetSystemMetrics` 查真实屏幕分辨率再传参。

### H.264 编码为什么要配一堆 "低延迟" 参数

看 `VideoEncoder.cpp` 第 60-74 行：



```
codecContext_->gop_size = 30;              // 每 30 帧一个关键帧（I 帧）
codecContext_->max_b_frames = 0;           // 不要 B 帧！B帧需要参考"未来"的帧，会增加延迟
codecContext_->flags |= AV_CODEC_FLAG_GLOBAL_HEADER; // 把 SPS/PPS 放进 extradata
av_opt_set(priv_data, "tune", "zerolatency", 0);    // 零延迟调优
av_opt_set(priv_data, "preset", "ultrafast", 0);    // 最快编码（代价：压缩率低、码率大）
```

理由：远程控制 / 直播要的是**实时**，画面晚到 1 秒比画质糊一点更难受。

不足（如实说）：`ultrafast` 会显著增大码率、浪费带宽；GDI 采集写 25fps、编码线程按 30fps 推，两边帧率不一致，长期会出现节奏漂移。

## 五、音频线程：攒帧 → AAC 编码 → 推送

`EncodeAudio()`（第 183-210 行）：



```
void RtmpPushManager::EncodeAudio()
{
    std::shared_ptr<uint8_t> pcm_buffer(
        new uint8_t[48000 * 8], std::default_delete<uint8_t[]>());
    uint32_t frame_samples = aac_encoder_->GetFrames();  // AAC 一帧要求的采样数（通常1024）

    while(!exit_ && isConnect)
    {
        if(audio_Capture_->GetSamples() >= (int)frame_samples)
        {
            // 数据攒够一整帧才读，不够就等
            if(audio_Capture_->Read(pcm_buffer.get(), frame_samples)
               != frame_samples) continue;

            AVPacketPtr pkt_ptr = aac_encoder_->Encode(
                pcm_buffer.get(), frame_samples);        // 编码
            if(pkt_ptr)
                PushAudio(pkt_ptr->data, pkt_ptr->size); // 推
        }
        else {
            std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 没货睡1ms
        }
    }
}
```

### 为什么音频要 "攒够 1024 帧" 才编码，而视频是一帧一帧编？

这是 AAC 格式本身的规定：**AAC 一帧（packet）固定封装 1024 个采样点**（`codecContext_->frame_size`）。编码器不接受零碎的半帧输入，所以必须攒。这也是 `GetFrames()` 存在的意义。

### 音频编码内部还有一次重采样（`AudioEncoder.cpp`）



```
codecContext_->sample_fmt = AV_SAMPLE_FMT_FLTP;  // 原生 AAC 编码器要 planar 浮点
...
// 输入 S16 整数 -> 重采样成 FLTP（浮点、平面排列）
audio_resampler_->Open(..., config.audio.format, ..., AV_SAMPLE_FMT_FLTP);
```

两个概念：



* **S16 vs FLTP**：整数 PCM vs 浮点；

* **packed vs planar**：packed 是 L,R,L,R 交错存放，planar 是所有 L 放一起、所有 R 放一起（`data[0]`、`data[1]` 分开）。AAC 编码器内部按 planar 处理更方便，所以 swresample 帮你转。

这也解释了为什么 `adjustFormatTo16Bits` 那个 bug 影响致命 —— 它声称输出 S16，但如果实际字节还是 float，这里重采样的输入解释就全错了。

## 六、RtmpPublisher：把裸流包装成 RTMP Tag

编码后的 H.264/AAC 还不能直接发，要加 RTMP 规定的 "标签头"。

### 1. 序列头的构造（`SetMediaInfo`，第 20-97 行）

AAC 序列头：



```
data[0] = 0xAF;   // 1010 1111：高4位10=音频，低4位 F=AAC、双声道、44k等
data[1] = 0;      // 0 = AAC sequence header（序列头），1 才是真正的音频数据
memcpy(data + 2, audio_specific_config, ...);
```

H.264 序列头（AVCDecoderConfigurationRecord）：



```
data[index++] = 0x17;  // 关键帧 + AVC
data[index++] = 0;     // 0 = AVCDecoderConfigurationRecord
data[index++] = 0x01;  // 版本
data[index++] = sps[1]; data[index++] = sps[2]; data[index++] = sps[3]; // profile/compat/level
data[index++] = 0xFF;  // 保留字节
data[index++] = 0xE1;  // 高5位保留，低3位=SPS个数(1)
data[index++] = sps_size >> 8; data[index++] = sps_size & 0xff; // SPS 长度（2字节）
// ... 然后 SPS、PPS 个数、PPS 长度、PPS
```

这就是 FLV/RTMP 里那套你可能在文档里见过的字节布局，代码是手工一个字节一个字节拼的。

### 2. 关键帧门控（`PushVideoFrame`，第 131-182 行）



```
if(!has_key_frame_) {
    if(this->IsKeyFrame(data,size)) {
        has_key_frame_ = true;
        rtmp_conn_->SendVideoData(0, avc_sequence_header_, ...);  // 先发视频序列头
        rtmp_conn_->SendVideoData(0, aac_sequence_header_, ...);  // 再发音频序列头
    } else {
        return 0;   // 第一个关键帧之前，所有 P 帧丢弃
    }
}
```

设计理由：解码器必须从关键帧 + 序列头开始，否则花屏。**等关键帧再开播是正确的行业惯例。**

### 3. 如实说这里的三个问题



1. **AAC 序列头错用&#x20;**`SendVideoData`**&#x20;发送（第 147 行）**。它是音频配置，应该走音频消息通道（`SendAudioData`），用视频通道发，对端可能把它当成异常视频包处理。

2. **音频在首个关键帧到来前全部被丢弃**（`PushAudioFrame` 第 190 行要求 `has_key_frame_`）。如果关键帧迟迟不来，开头会有一段无声。更合理的做法是音频序列头独立发送，不依赖视频关键帧。

3. **起始码判断有逻辑 bug**（`IsKeyFrame`，第 225-245 行）：



```
if(data[0] == 0 && data[1] == 0 && data[2] == 0)
    startcode = 3;                          // 要求第3字节是0
else if(data[0]==0 && data[1]==0 && data[2]==0 && data[3]==0)
    startcode = 4;
```

H.264 标准起始码是 `00 00 01`（3 字节）或 `00 00 00 01`（4 字节）。第一个分支检查 `data[2]==0`，但 3 字节起始码的 `data[2]` 是 **1**，匹配不上；4 字节分支又被放在 `else if` 里，且 3 字节起始码场景 `data[3]` 是 NAL 字节不是 0，也匹配不上。结果 `startcode=0`，取到的类型是错的。正确写法应判断 `data[2]==1`。

另外 `RtmpPushManager::PushVideo` 第 289 行无脑 `size - 4` 去掉 4 字节起始码，若编码器输出 3 字节起始码就会多切一个字节。

### 4. 时间戳



```
uint64_t timestamp = timestamp_.Elapsed();   // 从推流开始经过的毫秒数
```

音视频各自用 `Elapsed()` 打毫秒时间戳。不足：没有统一的时间基校准，音视频是两条独立线程各自取时间，长期运行后可能出现音画不同步；工业级实现会让音频时钟做主时钟，视频按音频时间对齐。

## 七、RtmpConnection：分块（Chunk）与发送

RTMP 规定消息要切成 Chunk 发送（默认 128 字节一块，本项目 `SetChunkSize(60000)` 调大，减少分块开销）。`RtmpConnection` 继承 `TcpConnection`，负责：



* 握手（`RtmpHandshake`，C0/C1/C2 那套）；

* AMF 信令（Connect → CreateStream → publish，`amf.cpp` 编解码）；

* 把 `RtmpPublisher` 给的消息通过 `SendRtmpChunks` 切块，写进 TCP 连接；

* 接收服务器回的 `_result` / `onStatus`，驱动状态机 `ConnectionState` 推进。

这部分和你在 ENET/RtmpServer 里学的服务端 Chunk 解析是**同一套协议的正反两面**：服务端 "拼块"，客户端 "切块"。
