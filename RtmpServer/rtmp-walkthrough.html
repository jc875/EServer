四个“号码”别混在一起

字段意义
fd本机 TCP socket，如 10、11。
CSIDChunk 通道号；项目发送用 3 命令、4 音频、5 视频、6 数据，这些是项目选择。
MSID / stream_id连接内的逻辑消息流。连接级命令通常用 0；createStream 返回后，publish/play 用返回值。

transaction ID 是一次命令请求与 _result 的配对号，另有用途，不能拿来当房间号。

02 / 初始化：此时还没有客户端

① main → EventLoop(2)：构造时就启动线程

源码节选：RtmpServer/main.cpp。后面的源码框都带有文件名和原始行号。

  1. EventLoop loop(2) 调用构造函数，构造函数立即调用 Loop()；不是等 main 再显式执行 loop。
  2. Loop() 建两个 EpollTaskScheduler，各有 epoll 实例和线程。线程进入 TaskScheduler::Start()，不断处理定时器与 I/O。
  3. RtmpServer::Create(&loop) 通过工厂创建 shared_ptr；它不是单例，每次调用都会创建对象。
  4. SetChunkSize(60000) 先修改服务器默认配置。新连接会复制这个值；接收分块大小仍从 128 开始，之后按对端通知更新。

② RtmpServer 构造 → TcpServer 构造：先接好回调

SetNewConnectCallback 只是保存一个 lambda，现在不执行。等 accept 得到 fd 后，它才调用虚函数 OnConnect(fd)。因为实际服务器是 RtmpServer，所以进入重写版本，创建 RtmpConnection，再由 AddConnection 强引用保存。

RtmpServer 自己还注册了一个 3 秒循环定时器：扫描 Session，清除 GetClients()==0 的房间。它不是每 3 秒新建房间。

③ Start → Acceptor::Listen：真正开始监听

Start(ip,1935)→socket / bind / listen→监听 Channel 注册 Scheduler 0

Listen 设置非阻塞、地址重用，然后把监听 Channel 的读回调设为 OnAccept，启用读事件，注册到 epoll。监听 fd 可读表示有新连接可以 accept；普通连接 fd 可读才表示有客户端数据可读。

④ 新连接 → RtmpServer::OnConnect → RtmpConnection 构造

本项目由 GetTaskSchduler() 轮询选择连接的 Scheduler；它可能选到 0，不能把本实现说成“主 Reactor 永远只负责 accept”。这里也没有另外一个专做业务的线程池；解析回调就在调度 I/O 的线程中执行。

构造顺序：先执行委托构造函数 → 先构造 TcpConnection 基类 → 准备 RtmpChunk 与状态 → 设置业务读/关回调 → 外层构造函数补充 handshake_ 和服务器 weak_ptr。

源码在 TcpConnection 基类构造时就注册可读 Channel，外层的 handshake_ 尚未初始化完成。这是构造期间过早暴露对象的并发风险；学习时要分清“设计意图中的完整初始化”与“代码是否保证完成后才接收回调”。

握手的 completed，究竟说明什么？

到达的内容Parse 做的事当前结果
C0 + C1，1 + 1536 字节数据不足就不消费；足够后检查版本 3，构造 S0+S1+S2 共 3073 字节并消费 C0C1。状态转 HANDSHAKE_C2；响应交给 TCP Send。
C2，1536 字节足够后消费，标记 HANDSHAKE_COMPLETE。没有额外握手响应。
C2 后紧接 connect ChunkOnRead 检查 buffer 剩余字节，立即调用 HandleChunk。不必等下一次可读事件。

握手完成仅表示可以开始解析 RTMP Chunk。此时还没完成 AMF connect，也没有通过 publish/play 加入房间。握手本身不是 type=20 的 RTMP 消息。

当前 Parse 一次只处理一个握手阶段。如果一批缓冲字节同时含完整 C0C1 和 C2，它只消费 C0C1，OnRead 又没有循环继续推进未完成的握手；没有新的读事件时，剩余 C2 可能停在那里。这与“C2+命令能在握手完成后继续解析”的分支是两件事。

HandleChunk：有进展，不等于有完整 Message

RtmpChunk::Parse 每次推进块头或块体阶段。ret>0 表示消耗了字节；ret==0 表示还不够，要等更多输入；只有 rtmp_msg.IsCompleted() 才能进入 HandleMessage。跨多块的消息在 rtmp_message_[csid] 中持续积累，不能每次读都重建解析器。

04 / HandleMessage：不是“命令、连接、数据”三个平级类型

connect 是命令名，位于 AMF payload；消息头 type_id 才是外层分类。不能用同一个表去比较 connect 和 8/9/20。

type_idpayload 是什么本项目怎么处理是否回复
20 / 0x14AMF0：方法名、事务号、命令对象、附加参数。HandleInvoke → connect/createStream/publish/play。按命令生成 _result 或 onStatus。
18 / 0x12AMF0 数据，如 @setDataFrame、onMetaData、属性集合。HandleNotify → 解析元数据 → Session 广播。转发数据，不给主播逐条回 _result。
8 / 0x08FLV 音频消息体，AAC 配置或 AAC 帧。HandleAudio → 判断序列头、缓存、广播。转发给观众，不回显给主播。
9 / 0x09FLV 视频消息体，AVC 配置或视频帧。HandleVideo → 判断序列头、缓存、广播。转发给观众。
1 / 0x014 字节大端新 Chunk Size。SetInChunkSize，改变接收方向。本分支不回包。
5 / 6确认窗口 / 对端带宽设置。本项目在 connect 后主动发送；接收分支未实现。default 当前忽略。
其他如用户控制 type 4、AMF3 命令 type 17 等。当前 switch 不支持，直接忽略。不能据此认为完整支持协议。

音视频消息体借用了 FLV 的音视频数据格式，但里面没有完整的 FLV 文件头，也不应再包上一整套 FLV Tag Header 才送进这里。

① HandleInvoke：先解方法名，再按 MSID 和方法分发




  1. reset() 清除上条消息的解码缓存。
  2. decode(payload,length,1) 解一个 AMF 值；返回的是所消费的字节数，不是值的个数。第一值为字符串方法名。
  3. stream_id==0 时，本实现接着解剩余参数，再识别 connect/createStream。
  4. stream_id==stream_id_ 时，解后续三个值（如事务号、null、流名），马上保存 stream_name_，拼出 stream_path_，再解 publish 的 "live" 或 play 的可选参数。


这里的 getString() 读取解码器缓存，不是再从 socket 收字符串；payload + bytes_used 表示跳过前面已解释的字节。stream_name 必须在继续解析 "live" 前取出来，否则最后读到的字符串可能已经变成发布模式。


这个 AMF 解码器不是通用的“值数组”：字符串、数字分别留在 m_obj 的字段中，属性放 m_objs。HandleConnect 的 getNumber() 在典型请求中得到事务号，是依赖后面的对象解码不覆盖该字段。新增命令时应该显式保存 transaction ID，别依赖这个偶然的缓存行为。

③ HandleCreateStream：_result 里哪个数才是 Stream ID？




客户端 → 服务端，消息头 MSID=0：
    ["createStream", 2, null]

服务端 → 客户端，初次响应消息头 MSID=0：
    ["_result", 2, {}, 7]
                 │      └─ 返回值：MSID=7（示例值）
                 └──────── 原请求的 transaction ID=2

客户端随后 publish/play 的消息头：MSID=7
payload 仍可有 transaction ID=0，它不是 MSID。


标准示意通常是 ["_result",2,null,7]；你的代码使用 encodeObjects(empty) 写空对象 {}。回复时 SendInvokeMessage 读取旧的 stream_id_，发送后才执行 stream_id_=stream_id，所以第一次 createStream 的响应头仍为 0。


这份源码不是 createStream 到来时生成编号。RtmpChunk 构造函数对静态 stream_id_ 执行 ++；GetStreamId 返回的是当前全局计数，没有给每个 Chunk 实例保存快照。若多个客户端先连入再 createStream，返回值可能相同，重复 createStream 也不能正确管理多条流。这种跨连接重号本身并不违反“MSID 在连接内有效”，但说明此分配器不能支撑完整的多流管理，也有并发访问风险。

06 / onMetaData：说明书，与 AAC/AVC 解码配置分开理解


内容常见形状用途此项目的通路
AMF 元数据{width:1280,height:720,framerate:25,videocodecid:7,audiocodecid:10,...}描述媒体属性；不包含视频画面，也不替代 SPS/PPS。type 18 → HandleNotify → SendMetaData。
AVC sequence header17 00 00 00 00 + AVCDecoderConfigurationRecord给解码器配置，含 SPS/PPS、NAL 长度字段大小等。type 9 → HandleVideo → SendMediaData。
AAC sequence headerAF 00 + AudioSpecificConfig说明 AAC 对象类型、采样率、声道配置等。type 8 → HandleAudio → SendMediaData。


所以你看到“Session 几乎都在调用 SendMediaData”是有原因的：音视频序列头也装在 type 8/9 中，并不走 onMetaData 的发送函数。项目注释把它们叫“音频/视频元数据”，容易把两个层次混在一起。


// 主播发送 type=18，payload 的语义：
["@setDataFrame", "onMetaData",
 ECMA_Array{width:1280,height:720,framerate:25,...}]

// 正确解析时，各段累计起点：
offset 0:   02 00 0D + "@setDataFrame"  // 16 字节
offset 16:  02 00 0A + "onMetaData"     // 13 字节
offset 29:  08 + 4 字节属性数量 + 属性内容 + 00 00 09

// 发给观众时常用：
["onMetaData", ECMA_Array{...}]     // 不带 transaction ID




问题一：累计偏移被覆盖。第一次 decode 消费 16 字节；第二次从 +16 解出 onMetaData，返回局部消耗 13，却赋值 bytes_used=13。下一次从原 payload+13 开始，实际应该从 +29 开始，可能从字符串中间乱解。不能把这个分支画成“已经正常收到元数据”。


// 建议修法的思路（伪代码，不是直接可替换函数）：
size_t offset = 0;
offset += decodeOne(payload + offset); // @setDataFrame
offset += decodeOne(payload + offset); // onMetaData
decodeMetadata(payload + offset);      // 从累计偏移 29 解
// 每步都要检查剩余长度、解码结果和类型。

// 此项目 AmfDecoder 的 ECMA_ARRAY 分支还有独立问题：
ret = decodeObject(data + bytes_used + 4, size - bytes_used - 4, m_objs);
// 跳过了 4 字节数组数量，却未把这 4 字节计入 ret/总消耗。
// 修偏移时必须同时修这个计数及边界检查。


Session::SendMetaData 与 Connection::SendMetaData 不是同一层




Session 遍历 weak_ptr，清掉过期项，只对 IsPlayer()==true 的连接调用接口。接着，虚函数实际进入那个观众的 RtmpConnection::SendMetaData。




问题二：函数完全没用传入的 metaData。它检查并编码观众连接自己的 meta_data_。正常观众从未发送过 @setDataFrame，该成员为空，直接 return false。Session 又没检查返回值，所以这个错误会悄悄发生。


// 建议修法（需要修好上游 AMF 解析，再配套缓存策略）：
bool RtmpConnection::SendMetaData(AmfObjects metaData) {
    if (IsClosed() || metaData.empty()) return false;
    amf_encoder_.reset();
    amf_encoder_.encodeString("onMetaData",10);
    amf_encoder_.encodeECMA(metaData); // 使用参数！
    return SendNotifyMessage(RTMP_CHUNK_DATA_ID,
                             amf_encoder_.data(),amf_encoder_.size());
}


此外，Session 目前没有缓存 AMF 元数据；即使修好上述两个问题，也只会发给元数据到达时已经在房间的观众。若要让后加入者收到，需要把解析成功的元数据缓存到 Session，并在加入/开始发送时补发。

① HandleAudio：AF 的高四位才是 AAC 格式编号


// AAC 常见头 AF = 1010 1111
sound_format = (payload[0] >> 4) & 0x0f; // 1010 → 10 → AAC
// 低四位 1111：SoundRate(2位)、SoundSize(1位)、SoundType(1位)
// 并不是音频 codec ID！AAC 的实际采样率/声道配置读 ASC。

// AF 00 12 10
payload[0] = 0xAF; // 音频格式等标记
payload[1] = 0;    // AACPacketType=0 → sequence header
payload[2..] = 0x12 0x10; // ASC 示例：AAC-LC、44100Hz、双声道

// AF 01 [AAC 数据...]
payload[1] = 1;    // AACPacketType=1 → 原始 AAC access unit
// 这里通常不是带 ADTS 头的 .aac 文件字节。




  1. 取高 4 位判断 AAC，且 payload[1]==0 时识别为配置。
  2. 复制整条消息体，包括 AF 00，缓存到发布连接，再调用 Session::SetAacSequenceHeader。
  3. 仅把传给 Session 的内部 type 改成 RTMP_AAC_SEQUENCE_HEADER=0x19。
  4. 无论是配置还是普通帧，都调用 Session::SendMediaData。服务端不解码成 PCM。


源码里 code_id=payload[0]&0x0f 的注释写成“编码 ID”，对音频是错的，且该变量未使用。只有在音频格式确认是 AAC 后，payload[1] 才有这里的 AACPacketType 含义。读取前至少检查长度 2；AAC 配置还需验证后面的 ASC。


② HandleVideo：17 与 27 是怎样拆出来的？


0x17 = 0001 0111
       └─┬─┘└─┬─┘
      帧类型1 编码7(H.264/AVC)
0x27 = 0010 0111 → 帧类型2（inter frame）、编码7

// AVC 配置包（不是画面帧）：
17 00 00 00 00 [AVCDecoderConfigurationRecord，含SPS/PPS等]
│  │  └──┬───┘
│  │   CompositionTime（3字节）
│  └─ AVCPacketType=0：配置
└─ FrameType=1 / CodecID=7

// AVC 视频数据包：
17 01 00 00 00 [NAL长度][NAL内容][NAL长度][NAL内容]...
27 01 00 00 00 [NAL长度][NAL内容]...
   └─ AVCPacketType=1：NALU 数据
// NAL 长度字段大小由配置中的 lengthSizeMinusOne 决定；常见为4字节。
// 不要默认这里使用 Annex B 的 00 00 00 01 起始码。
// AVC NALU 消息的 RTMP 时间戳通常表达 DTS；PTS=DTS+有符号CompositionTime。




判断 frame_type==1 && codec_id==7 && payload[1]==0，就缓存整条 AVC 配置消息体并打内部标记 0x18。普通视频体不做解码，直接交给 Session。AVC 包的前导结构至少需要 5 字节；本函数当前没有对应边界检查。


0x18/0x19 是项目内部标记，不是线上新消息类型。SendMediaData 最终把它们映射回视频 type=9、音频 type=8，所以接收方仍按标准格式解析。不要把内部 0x18 和 payload 第一个字节 0x17 混为一谈。



08 / Session 广播：不是把主播的 TCP 包原样转发




  1. 锁住 Session，遍历 rtmp_sinks_；过期 weak_ptr 会被清理。
  2. 只给 IsPlayer() 的连接发，不回发给主播。
  3. 如果观众 !IsPlaying()，先尝试送缓存的 AAC 配置，再送 AVC 配置；随后送本次数据。
  4. 这些调用进入每个观众 Connection 的 SendMediaData；它各自重新创建 Message 和 Chunk。


如果主播 MSID=7、观众 MSID=8，观众收到的音视频消息必须使用它自己的 8。Session 共享的是消息体内容，不是照搬主播所有 Chunk Header。配置还没到时缓存大小为 0，发送函数返回 false；这里也未检查返回值。


观众 Connection::SendMediaData：缓存、等待关键帧、封装




先检查连接关闭与空包，再设置 is_playing_=true。注意它只表示发送路径已启动，不保证解码器已经显示画面。内部配置类型会更新观众自己的配置缓存。之后按项目的关键帧条件筛包，再设置：


// 以下对应上面源码的封装部分：
rtmp_msg._timestamp = timestamp;
rtmp_msg.stream_id = stream_id_; // 观众自己的流编号
rtmp_msg.playload = playload;    // 共享媒体消息体
rtmp_msg.lenght = playload_size;

// 视频/AVC配置 → type_id=9，CSID=5
// 音频/AAC配置 → type_id=8，CSID=4
SendRtmpChunks(csid,rtmp_msg);


当前“等关键帧”判断同时作用于普通音频和视频，并且 IsKeyFrame 只检查首字节高/低四位，没检查消息类型或 AVCPacketType。已有 AVC 配置时，音频也可能在首个关键帧前被丢弃；而在 AVC 配置还没收到时，这个门槛根本不生效。它不等于严格的解码起播保障，也没有 GOP 缓存。

09 / 关闭：从连接身份退回资源管理


socket EOF / 错误 / 业务回调返回 false
  → TcpConnection::Close()（只执行一次）
      is_closed_=true
      Scheduler::RmoveChannel(channel_)
      closeCb_ → RtmpConnection::OnClose()
          → HandleDeleteStream()
          → 1ms 定时器中 Session::RemoveSink(conn)
      disconnectCb_ → TcpServer::RemoveConnection(fd)
  → 没有强引用后析构 TcpConnection，close(fd)
  → 3秒定时器清理零客户端的 Session


代码把 RemoveSink 放进短定时器，因此它会暂时强持有 conn。另一方面，HandleDeleteStream 在定时器执行前就清掉 is_playing_/is_publishing_，但没有把 state_ 改离 START_PLAY/START_PUBLISH；IsPublisher 依据 state_ 判断，当前 RemoveSink 仍可识别主播。理解时不要把 state_ 与两个布尔量当成同一个变量。


协议的标准命令名是 deleteStream，该代码只匹配 "DeleteStream"，并且套在流级命令解析里；它没有正确实现标准 deleteStream 的参数/路由。连接断开触发的 OnClose 清理则是另一条路径。



10 / 源码事实核对：哪些地方不能照着当协议规则？


下面是阅读发现，未在本次任务中修改服务端。原有注释也有不准确之处，应以函数体和协议字段含义为准。


位置实际问题影响 / 学习重点
HandleNotify第二次 decode 覆盖累计偏移；只处理 @setDataFrame 包装，不处理直接 onMetaData。元数据解析不可靠；需要按累计字节推进并检查每次结果。
AmfDecoder::decodeECMA Array 跳过数量4字节却漏计消耗；部分失败只 break，外层未必得到负错误码。不能仅凭 bytes_used<0 就认为解码安全；还需类型/边界验证。
Connection::SendMetaData不用参数，改用观众自己的空成员 meta_data_。正常播放器收不到转发的 AMF 元数据。
Session只缓存 AAC/AVC 配置，不缓存 AMF 元数据或 GOP。后加入者没有元数据补发；要等未来关键帧，不会立即回放最近 GOP。
HandleAudio / Video未检查 payload 的最小长度、连接发布身份及目标 MSID。会越界，也不能把这套分支当成完整的协议状态校验。
HandlePlayonStatus 缺 command object 占位；也未发送常见 StreamBegin 用户控制消息。客户端兼容性不完整；源码发包序列和规范典型序列需分开看。
RtmpChunk::GetStreamId返回共享静态计数，而不是连接私有已分配值。分配时机与并发管理不完整；每连接只有一个 stream_id_，并不支持完整多流。
时间戳转发Parse 完成后累计时间在 _timestamp，但 HandleAudio/Video 传给 Session 的是 timestamp。增量/扩展时间可能转发错误。不能直接说两字段等价；Clear 清 timestamp 也不等于清 _timestamp。
SetChunkSize 分支不验证4字节长度、零值和有效范围。后续可能除零、异常内存/状态行为；只说明有此入口，不等于健壮实现。
事件线程 / 发送队列构造时过早注册 Channel；跨连接发送、队列满返回值也未完整处理。存在并发与慢观众处理缺口；本页没有把教学示例说成生产级服务器。


读完后用一句话走通这条链：
网络层读到字节 → OnRead 完成握手 → HandleChunk 拼出完整 Message → HandleMessage 按 type_id 分支 → 命令解 AMF 并更新连接/房间，媒体检查前导字段并缓存配置 → Session 找到观众 → 观众 Connection 用自己的 MSID 重新分块 → TCP 写缓冲 → send。
关键区别：命令的回复通常回原连接；主播媒体经过 Session 发给观众连接；AMF 元数据走 SendMetaData，AAC/AVC 配置随音视频走 SendMediaData。
